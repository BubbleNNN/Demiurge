# 昔涟形象生成流程审计

审计日期：2026-09-30。范围：内置素材的制作方式、当前 API 生成代码、角色身份保持的公开工作流。原始审计记录如下，代码行号指审计时的版本。后续实现进展见文末；流程修复不等于已经完成昔涟出图验证。

## 结论

首张基准图没有由经过核验的原角色图像约束；后续以生成图为参考，只能保持这张图的一致性，不能证明它还原了昔涟。此前验收偏重画面美观、风格数量和运行能力，漏掉了原角色还原度。

需要区分两条路径：

- 内置 `public/art/cyrene-*.png` 是开发期间使用图像生成工具制作的素材。制作时先用文字生成立绘，再以生成立绘衍生其他风格，没有建立官方图像参考包和还原度验收记录。这些素材不是通过应用内 `generateSkin` 产生的。
- 应用内 `generateSkin` 存在同类设计缺陷：每次选择一种风格，先以文字生成一张新基准图，再用该基准图编辑五种表情。五种表情分别直接引用同一基准图，并非依次引用上一张表情；这一点有助于减少链式漂移，但不能纠正基准图本身的身份错误。

## 公开工作流中值得采用的机制

1. **以真实图像建立角色条件。** [BFL 的角色一致性说明](https://docs.bfl.ai/guides/usecases_editing_character_consistency)使用一张或多张角色参考图，再描述需要改变的场景或姿态；[多图编辑指南](https://docs.bfl.ai/guides/prompting_editing_multi_reference)要求说明每张输入图的用途。对 Mori 而言，应将角色参考与画风参考明确区分，避免把风格图中的人物特征也迁移进来。
2. **工作流中必须真的连接图像输入。** [ComfyUI 官方 Qwen-Image-Edit 示例](https://docs.comfy.org/tutorials/image/qwen/qwen-image-edit)包括 Load Image，并将输入图用于语义和外观控制。[Comfy 官方多图 Kontext API 模板](https://github.com/Comfy-Org/workflow_templates/blob/main/templates/api_bfl_flux_1_kontext_multiple_images_input.json)也显式加载并组织参考图。接口名字、模型名字或一段 prompt 不能替代这条数据流。
3. **外观与姿态可以分别约束。** [Tencent IP-Adapter](https://github.com/tencent-ailab/IP-Adapter)提供图像提示与文字组合、结合 ControlNet 的示例；[ControlNet](https://github.com/lllyasviel/ControlNet)提供姿态、边缘等空间控制。它们是可选实现手段，需要在二次元角色与目标画风上验证效果，不能直接等同于角色还原保证。
4. **Live2D 依赖合格的原画。** [Live2D 官方素材分离流程](https://docs.live2d.com/en/cubism-editor-manual/divide-the-material/)从原图拆分眼睛、睫毛、轮廓等部件，并补绘运动后会露出的区域。原画身份错误不会在拆分或绑定阶段自动修复。当前项目已接入模型导入与运行，不等于已实现可靠的自动原画制作与绑定。

这些资料支持上述具体机制；下面的完整流程是针对 Mori 的工程设计建议，不是声称存在一套拿来即用、已经验证全自动还原所有角色的产品。

## 建议替换的流程

```text
名字、作品、目标形态
    ↓
检索候选来源 → 核验发布者与角色版本 → 获取实际参考图
    ↓
角色参考包 + 可追溯的视觉特征约束
    ↓
使用参考图生成少量候选基准图
    ↓
对照原作参考做身份验收 ── 不通过 → 有界重试 / 等待补充资料
    ↓ 通过
冻结已验收基准图
    ↓
原始参考 + 基准图 → 各种风格变体 → 各风格再次验收
    ↓
各风格基准 → 局部表情编辑 / 分层原画 → 动画与模型制作
    ↓
聊天、表情与动作运行时
```

### 参考包与不可变特征

- 将原角色、作品、目标服装/形态分别记录。资料冲突时保留冲突，不能把不同形态自动混成一个人。
- 优先同一形态的官方全身图、脸部细节、服装细节，用户提供的指定参考也可作为明确的目标。背面等未展示部位应标为未知，不自动升格为原作事实。
- 每张参考记录来源页面、实际图像来源、发布者核验状态、用途、形态和内容哈希。生成资产另记父资产、参考 ID、提示词版本、模型/参数以及验收结果。
- 视觉约束应包含发型与刘海轮廓、眼睛特征、关键饰物及位置、服装裁片/剪影、颜色在不同部位的分布。像素或毛绒风格可以简化细节，但要明确保留哪些辨识特征。
- 对像素、毛绒、Q 版，改变的是媒介、纹理与比例；发型、标志性配饰和服装关系不能任由“更精美”类修饰语重新设计。

### 生成与验收

- 没有可用参考或资料仍为“暂无可靠资料”时，不进入“还原现有角色”的生成路径。原创角色是另一种明确的任务模式。
- 基准候选阶段与表情扩展阶段分开；未通过身份验收，不启动整套衍生生成。
- 每种风格都重新参照原始角色证据，避免像素图成为毛绒图唯一的身份来源。
- 表情优先采用模型支持的局部编辑或遮罩；仅写“只改表情”不是像素级不变保证。仍需检查发型、衣服及画面位置是否被改动。
- 视觉模型可以输出逐项差异和疑点，辅助筛选；不要使用未经校准的“相似度 90%”充当验收结论。调试阶段需要人工对照原参考，积累可复核的样本。
- 自动重试须有次数与预算上限，保留失败候选和失败原因，不能无限优化 prompt 直到任意图像被判为成功。

### 保持 API 方案

桌面端仍可负责检索、参考管理、任务编排和预览，图像编辑使用支持参考图的云端 API。针对不同提供商声明能力：参考图数量、局部遮罩、透明输出、姿态条件、异步任务等。不能假设所有“兼容接口”都具备同一编辑能力；缺少身份参考能力时应明确报告，而非悄悄退回文生图。

IP-Adapter/ControlNet 是可选的托管工作流路径，不要求所有用户在本机安装 GPU 环境。具体服务、模型和参数需以昔涟样本验证后选择。这里没有进行付费模型对比，不能据文档宣布某个模型已经解决本项目的还原问题。

## 优先级与验收标准

P0：参考资产与角色形态的数据结构；参考图输入的图像服务适配；禁止未知外貌进入还原路径；首图与衍生分阶段；保存来源与验收状态。

P1：角色约束检查、有限重试、风格分支复核、局部表情编辑。

P2：通过验收的分层原画、Live2D/其他动画资产制作及运行时映射。

昔涟的第一项验收应是：能并排展示明确版本的原作参考与候选图，并逐项说明身份特征是否保留。通过之后再验证多风格和动作能力。单元测试补充验证“缺参考时不发生成请求”“未验收不扩展”“每个风格确实传递原始参考”等机制；视觉还原度仍必须独立验证。

## 后续实现：原图直接输入（2026-09-30）

根据用户确认，角色参考图直接作为图片文件输入，不先抽象为文字再还原：

- 已增加本地原图导入与预览、来源页面记录、角色包持久化；每个角色 1–4 张图，原文件字节保留。
- 已将新候选入口切换到 Images Edits：只有真实图片可启动任务。文字外貌即使未知，只要有有效原图也可以生成；没有原图则停止。
- 首图与表情已拆成独立阶段。候选并排对照原图，人工确认后才启用扩展；错误候选可以标记为需重做。
- 跨风格生成始终包含原图，可增加已确认基准；每张表情同时引用基准和原图。保存参考内容与基准内容的哈希，旧确认不能用于变化后的资产。
- 已补充传输、审核门槛、失效拦截、存储往返、失败续传测试。内置早期立绘标记为未核对，不会自动成为可信参考。

尚未完成：自动获取/核验官方原图、自动视觉质量评估、局部遮罩编辑、重新生成并验收昔涟。测试服务只证明请求携带了原图，不代表图像还原度通过。

## 后续实现：公开收图与 3D 制作（2026-10-01）

已补上公开社区索引和已有网页/Wiki 的实际图片下载，保留原始像素、来源、尺寸与匹配状态。昔涟和风堇均已真实取得 2048×2048 的社区目录立绘并完成文件哈希校验；名字匹配不等于官方发布者或角色形态核验。没有参考时可以采用匹配立绘，已有参考保持原样；网页候选由用户选择。可直接将主参考用作静态外观，或继续经图像编辑接口制作新画风。
